# VS Code 现代化 UI 改版

原文：[Modernizing the VS Code UI](https://code.visualstudio.com/blogs/2026/10/15/modern-ui)，2026 年 10 月 15 日，作者 Lee Murray，发布于 VS Code 官方博客。以下为全文翻译（图片说明一并保留），个别括号内是我的补充。

## 正文翻译

自 2015 年首次预览以来，VS Code 已经改变了很多。标签页、主题以及组织工作的新方式让它更加强大，但十多年来不断新增和打磨功能，也给整个工作台带来了视觉上的复杂和不一致。

这次现代化并不是要重新发明编辑器。我们要做的是打磨这个熟悉的界面：让层级更清晰、减少干扰，并为 VS Code 建立一套共享的设计基础，既能支撑编辑，也能支撑 agent 会话这类较新的工作流。目标是更加连贯、更平易近人的体验，同时不放弃开发者所依赖的信息密度、自定义能力和肌肉记忆。

现代化 UI 今日已开放预览。这项工作始于 2026 配色主题，经由 Agents 窗口扩展进行，如今正在塑造编辑器本身。在这篇文章中，我们会讲述这次现代化是如何演进的，以及你的反馈如何继续塑造它。

## 一个一直在演进的界面

有些界面改动只是小的打磨，有些则引入了组织工作的新方式。即使是如今感觉像编辑器「原生功能」的特性，其实也是逐步到来的。

时间线依次标出了：2015 年首次预览、2016 年的编辑器标签页、2019 年的全新树控件、2023 年的 Dark Modern 和 Light Modern 主题，以及 2026 年的现代化 UI 预览。

（配图：旧的工作台设计，我们称之为 classic UI 经典界面，与现代化 UI 预览的对比。）

每个功能在引入之后我们都在持续打磨，参考的是来自不同主题、布局和工作流的反馈。当前的现代化遵循同样的路径。

## 第一步：颜色

颜色是你把 VS Code 变成「自己的」编辑器的一部分，但它也决定了你阅读界面的速度。一个均衡的配色能让重要的内容和状态凸显出来，而不会让工作台的每个部分都在抢注意力。

我们通过 Dark 2026 和 Light 2026 主题开始了这段现代化旅程。我们把工作台配色和语法高亮当作一个整体体验来看待，由此确立的视觉基础后来被带入了现代化 UI。收窄的表面色范围建立了更清晰的层级，让代码始终处于中心；更一致的悬停、聚焦、选中、校验和 agent 状态，让界面在亮色和暗色环境下都能被清楚地阅读。

（配图：Dark 2026 和 Light 2026 主题。）

颜色给了我们一个起点，但要打造更连贯的界面，还需要一套覆盖间距、字体、表面和控件的共享规则。机会来自一种新形态的 VS Code 窗口。

## 一个 VS Code，不同的工作方式

Agents 窗口已在 2026 年早些时候以预览形式进入 Stable。它把完整的 agent 工作流集中到一处：从发起会话、跟进进度，到审查结果。它代表了 VS Code 中一种新的工作方式——以「委派任务、随进度审查工作」为中心。支撑这种转变需要一套全新的界面方案，让会话状态和下一步操作一眼可扫，同时不会挤占提示词和审查区域的空间。

我们正在让 Agents 窗口和编辑器窗口在字体、间距、颜色、标签页和控件上对齐到同一套方案。在两者之间切换，应该感觉像是换了种工作方式，而不是换了个产品。这并不意味着把布局做得一模一样，也不意味着让所有人的 VS Code 长成同一个样子。每个窗口仍然为各自的用途做了优化，你仍然可以选择主题、调整密度，按自己的屏幕和工作流来布置工作区。

既有的工作台是围绕「直接与文件交互」设计的，并且是一个组件一个组件长出来的。间距、字体、表面和控件并不总是遵循同一套系统，这让界面难以适配新的工作流，也难以把改进跨窗口复制。Agents 窗口给了我们一个地方去发展那套共享的设计系统。

我们一起梳理了这些设计决策，并验证它们能否支撑会话管理、进度跟进和变更审查。最终得到的是一套可以贯穿整个 VS Code 持续打磨的共享视觉语言，而不是给 Agents 窗口做了一个独立的身份。

（配图：Agents 窗口把界面组织围绕 agent 会话与审查其工作展开。截图展示的是更新后的设计系统的早期实现。）

当这些决策在 Agents 窗口里协同生效之后，下一个问题是：这套系统能否支撑编辑器？编辑器带来了不一样的需求，包括密集的文件导航、多个编辑器组，以及早已习惯的工作流。

把共享系统引入这个环境，成了现代化的下一阶段。我们没有去重新设计文件编辑本身，而是从共享的工作台外壳开始：那些在各种工作流中人们都会看到、用到的核心区域和控件。这些元素定义了界面如何组织、人们如何在其中移动。从这里入手，让我们既能提升一致性，又能保留密集导航、多编辑器组和长期形成的交互模式。

随着工作台不断生长，活动栏、侧边栏、编辑器组、面板、标签页和状态栏这些相关部分，对同样的设计问题发展出了各自不同的解法。初期工作聚焦于：

- 清晰地划分工作台的主要区域，又不让它们显得彼此割裂。
- 让调整大小和移动面板的控件更容易被发现。
- 简化字体排版和视觉层级，让你的工作内容始终是焦点。
- 对间距、圆角、颜色和阴影高度采用统一的标准。
- 刷新标签页，同时保留自定义能力。

共享的设计 token（design tokens）为间距、尺寸和颜色提供了统一的命名值，而不是在每个组件里各自定义。这让我们可以一致地调整界面，并支持不同的密度和主题。

（配图对比：之前——编辑器与 Agents 窗口的布局是围绕各自工作流独立设计的。为做同口径对比，两个窗口都用 Dark 2026 主题、同一尺寸。现在——共享设计系统让两个窗口有了更强的家族相似性，同时各自保持为自身用途优化，主题与尺寸同前。）

## 分阶段推出，并从反馈中学习

我们分阶段推出现代化 UI，以便在设为默认之前，先从越来越广泛的开发者群体中学习。它最早作为 Stable 中的实验性设置出现，随后在 Insiders 中默认启用。接着我们在 Stable 中对一部分用户做了受控实验。从这次推送学到经验之后，我们对所有人默认启用，同时在过渡期保留了回到经典 UI 的选项。

随着预览触达更多人，我们的设计假设开始接受现实检验：不同的显示器、缩放级别、主题和工作流。我们开了一个公开的反馈讨论帖，开发者们分享了几十个非常具体的例子。我们把这类反馈与单条的 issue 报告以及团队自举（self-hosting）结合起来，从中归纳出模式，而不是把任何一张截图或个人偏好当成普适结论。

几类共同的主题浮现出来：

- **整体密度**：留白和面板内边距挤压了代码、树状列表行和终端输出的空间，在小屏幕和带多个编辑器组的布局上尤其明显。
- **编辑器标签页**：胶囊式设计让当前文件看起来像是脱离了它的编辑区，而标签页的标题和操作按钮又在有限的横向空间里互相争抢。
- **状态栏**：更宽的条目间距，意味着在被隐藏之前能容纳的信息变少了。
- **面板边界**：分隔线和调整大小的控件需要容易找到，但又不能在视觉上太抢眼。
- **主题与对比度**：主题使用者和作者都需要对新表面、边框和激活状态有更多控制。
- **响应性**：一些报告指出工作台更新时有渲染性能问题。

在 1920 × 1080、100% 缩放的显示器上，现代化 UI 目前大约多占用 20 px 的横向空间和 12–18 px 的纵向空间（取决于布局）。我们加这些空间是为了分隔内容、让控件更容易找到，但这也意味着留给你的工作区域变少了。反馈凸显了为不同布局提供更好平衡的重要性。

## 你的反馈如何改变了设计

### 布局密度

我们听到的意见是：如果「更宽敞的界面」意味着能看到的代码或项目内容变少，那它就谈不上改进。这些反馈促使我们实现了布局密度（Layout Density）。

紧凑密度（Compact）在保持现代化 UI 的结构和自定义能力的同时缩小间距。它面向小屏显示器、信息密集的工作流，以及所有偏好更紧凑布局的人。配合主题和颜色自定义，它可以给你一个更接近旧界面的布局，同时保住新的基础。

要使用紧凑密度，可以从标题栏打开「自定义布局」（Customize Layout），选择 Layout Density > Compact，或者设置 `window.density.layout` 为 `compact`。

（配图：默认密度与紧凑密度，同一窗口尺寸、主题、打开的视图和编辑器内容。）

### 重新设计的编辑器标签页

最近，关于编辑器标签页的反馈促使我们重新审视它的设计。你用标签页来导航文件、分辨哪个内容是当前活跃的，所以标签页与编辑区的关系很重要。

最初的胶囊形标签页看起来像是悬浮在编辑器上方的独立控件。这让选中的文件很难在视觉上与它的内容关联起来，尤其是在激活状态颜色比较含蓄的主题里。改成连接式标签页（connected tabs）之后，选中的标签页会与下方的编辑器表面连为一体，标签页和内容呈现为一个连续的区域，恢复了「当前文件」这一熟悉的视觉线索。

（配图：胶囊标签页与连接式标签页，截自相匹配的生产组件样式。）

如果你更喜欢胶囊设计，仍然可以通过 `workbench.experimental.modernUIEditorTabStyle` 设置选回它。

### 更小的工作台打磨

反馈还带来了一些散布在工作台各处的小改动：

- 简化字体排版，移除了全大写标签。
- 打磨间距、圆角和颜色，建立更一致的层级。
- 调整了面板分隔与缩放控件。
- 为编辑器标签页提供了更多控件。
- 重新审视了状态栏的间距。
- 扩展了现代化 UI 元素的主题自定义。

使用这些打磨你不需要改任何设置。以下可选设置提供更多控制：

- `workbench.experimental.modernUIUppercaseViewHeaders`：让视图标题、侧边栏标签和面板标签使用全大写文本。
- `workbench.activityBar.compact`：使用更窄的活动栏尺寸，为界面腾出更多横向空间。
- `workbench.editor.tabActionReserveSpace`：控制现代化 UI 中标签页是否始终为操作按钮保留空间。关掉它可以让干净的未激活标签页更宽敞。

名字里带 experimental 的设置在设计稳定之前可能变化或被移除。其余设置是受支持的自定义项，而不是强制迁移步骤。

### 对主题作者意味着什么

颜色主题是开发者个性化 VS Code 的主要方式之一，背后有活跃的主题作者社区。在为现代化 UI 更新和扩展内置主题的同时，我们也将新的颜色控制项开放给了扩展作者。

既有主题在现代化 UI 和经典 UI 下都保持兼容。现代化 UI 的新颜色 ID 会回退（fallback）到既有工作台颜色，因此没有定义这些 ID 的主题会保持原有配色。

主题作者可以选择采用新 ID，以更精细地控制表面、边框、标签页、活动栏和窗口状态。这些 ID 还是实验性质的，因此请在现代化界面与经典界面下、在亮色、暗色和高对比主题下分别测试所有覆盖值。

现代化 UI 的主题指南（theming guide）记录了完整的 token 列表、默认值、优先级规则、高对比行为和示例。既有的 Color Theme 指南则说明如何打包和发布一个主题扩展。

### 保持现代化 UI 的响应性

视觉一致性不能以牺牲响应性为代价。一些反馈报告提到了渲染性能，于是我们用浏览器 trace 和可复现的基准测试进行了排查。

当 UI 发生变化时，浏览器需要重新计算哪些样式生效。过于宽泛的 CSS 选择器会让这项工作比必要的更昂贵。在第一轮选择器修复中，我们把那些需要检查大范围 DOM 的选择器，替换成了组件本来就知道的状态类（state classes），比如「是否显示了 diff 概览」或「是否存在调试操作」。

我们用一个可复现的常见工作台操作序列来度量这些改动：调整窗口大小、切换视图、滚动、打开 diff、运行控件动画。在这一综合基准中，这些修复让样式重算时间降低了 8.2%，总耗时（wall-clock）降低了 3.3%。布局时间增加了 6.6%，所以整体上仍未能完全追平旧界面的耗时水平。

这些是针对性的改进，而不是宣称整个工作台变快了。为了防止同样的模式卷土重来，lint 规则会拒绝已知的高开销选择器，并且 `npm run perf:css` 给了我们一个可复现的基准用于验证未来的改动。

## 接下来

现代化仍在演进。今天，你可以在更新后的界面和旧版 VS Code 工作台设计（我们称之为经典 UI）之间选择。随着时间推移，我们计划让经典 UI 退役，以便把改进精力集中在共享的基础上。

在过渡期间，你可以回到经典 UI：打开设置，搜索 `workbench.experimental.modernUI`，取消勾选即可。这个选项是暂时的——虽然我们还没有定下移除它的日期——我们会在过渡结束前公布时间表并提前通知。

在那之前，我们会继续：

- 在保留各工作流所需东西的前提下，让 Agents 窗口和编辑器窗口的共享控件与样式保持对齐。
- 根据关于对比度、可读性和语法颜色方面的反馈，继续打磨 Dark 2026 和 Light 2026。
- 打磨标签页的样式与自定义。
- 分析渲染开销，并用可复现的工作台度量验证进一步的改进。
- 针对具体的反馈调整密度、布局控件和其他细节。
- 让布局密度及相关自定义项更容易被发现。

感谢你帮助我们改进设计。工作台上这些较大的更新和较小的打磨，都反映了我们从你身上学到的东西。请继续分享哪些地方好用、哪些地方碍事。你不需要用设计术语，也不需要给出修复方案——一张截图，加上显示器、缩放级别、主题、设置和工作流的说明，就能帮我们理解问题。如果你回到了经典 UI，请告诉我们更新的界面还需要改进什么，才能成为唯一的界面。
