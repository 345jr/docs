# 图像为什么可以被压缩

原文是 MDN 博客上 Polina Gurtovaia 写的图像格式三部曲（2025 年 5 月～11 月陆续发布）：

1. [Color models for humans and devices](https://developer.mozilla.org/en-US/blog/color-models-humans-devices/) —— 颜色是怎么被感知和表示的
2. [Pixel data from encoders to decoders](https://developer.mozilla.org/en-US/blog/image-formats-pixels-graphics/) —— 像素数据如何被编码和解码
3. [Codecs and compression tools](https://developer.mozilla.org/en-US/blog/image-formats-codecs-compression-tools/) —— 格式与工具的实战选型

读完之后我的整体感受是：它表面上在讲「选哪个格式」，实际上回答的是一个更根本的问题——**为什么图像可以被压缩**。三篇文章分别从感知、算法、工程三个层面回答它，读下来像一条完整链路，而不是三篇独立的科普。

## 一句话概括

**图像压缩不是「更省地存像素」，而是理解人眼和设备的特性之后，有策略地丢弃信息。** 明白了这条链路，格式之争就不再是「谁更好」，而是「在什么场景下，用哪些参数，丢哪些信息」。

## 第一层：为什么可以丢（人眼）

这是整个系列最反直觉、也最关键的一层。图像格式的设计前提不是「忠实记录像素」，而是「记录人眼真正在意的东西」。而人眼有几个明确的偏好：

- **对亮度远比对颜色敏感**。所以可以把亮度（Y）和色度（UV）拆开，颜色通道粗一点、亮度通道细一点——这就是色度下采样和 YUV 空间存在的意义。
- **对低频敏感、对高频不敏感**。所以可以丢掉细小的纹理和噪点，把图像分解成不同频率再砍掉高频——这是 DCT 变换的立足点。
- **对暗部更敏感**。所以用 gamma 校正（≈2.2）把更多比特分给暗部，而不是均匀分配——这也是为什么「感知上的中灰」其实是 180 左右，而不是 128。
- **对结构比对颜色距离更敏感**。所以才有 SSIM 这类贴近感知的质量指标，以及 L\*a\*b\*、Oklab 这类「感知均匀」的色彩空间。

换句话说，**能被压缩的部分，几乎都能追溯到某条人眼的局限**。颜色是大脑对电磁波的解释，而压缩就是在利用这个解释的粗糙之处。

## 第二层：怎么丢（编解码器）

现代编解码器虽然名字各异，但基本都在跑同一套流水线，只是每步的实现和参数不同：

```
YUV 分离 → 色度下采样 → 分块 → 预测 → 变换(DCT) → 量化 → 熵编码 → 后处理滤波
```

几个我觉得值得记住的点：

- **预测 + 残差**：先猜块里大概长什么样（用周围像素或固定图案），只存「猜错的部分」。AVIF 有 71 种预测模式，WebP 10 种，JPEG 干脆不用。
- **变换 + 量化才是真正丢信息的地方**。DCT 只是把信息按频率拆开，量化（除以一张量化表）才是把高频系数变成零的那一步。JPEG 的「质量」旋钮本质上就是在缩放这张表。
- **熵编码负责最后瘦身**。高频出现的值用更少比特（Huffman），更先进的用算术编码逼近香农熵极限。这解释了为什么纯色图能压到几百字节，而随机噪声压不动。
- **交错（渐进加载）几乎免费**。重排系数让粗略版本先到，代价接近零——但 PNG 的交错是例外，它会变大。

一个容易被忽略的结论：**格式往往是视频编解码器的副产品**。AVIF 基于 AV1，WebP 基于 VP8。编解码器演进更快，图像格式常常是顺手摘下来的果子。

## 第三层：怎么选（工程实践）

第三篇用一堆实验把「选格式」这件事从玄学拉回工程，我认为最有价值的是它拆穿了两个常见误区：

**误区一：拿两个格式的「质量数字」直接对比。** 实验里 AVIF 一开始「输给」JPEG，查日志才发现 AVIF 被设成了 12-bit / YUV444，压根没做下采样。不同编解码器的质量参数含义不同，**参数不对等，比较就没有意义**。

**误区二：用 MSE / PSNR 判断画质。** 这类指标对少量差异像素过度惩罚、忽略结构和色彩。换成 SSIM（更贴近人眼）之后，AVIF 在低质量区间明显胜出。质量本身还是主观的——「消失的乌鸦」那张图就说明，数学指标可能更偏爱「干净但丢了主体」的版本，而人不会。

除此之外，文章反复强调一个事实：**同一格式内部的差异，常常比格式之间还大**。同样是 Q=75 的 JPEG，MozJPEG 比 Chrome 内置编码器小 30%；开不开色度下采样又是另一个量级。

落地上，作者的排序也很务实：优先用云服务做按需处理 → 入门先用 MozJPEG 的 `Q=75,strip,interlace` → 进阶用 `<picture>` 提供多格式 → 能懒加载就别提前加载 → 最后持续统计、主动优化。还有一条容易被忽视的：**尽量别用 PNG**，无损场景用 WebP / AVIF 更划算。

## 我读完之后留下的三句话

1. **压缩的本质是「有损于像素、无损于观感」。** 所有算法都在回答同一个问题：哪些信息人眼根本不会在意。
2. **没有最好的格式，只有最合适的参数组合。** 「JPEG 还是 AVIF 好」这个问题本身就是错的，正确的问题是你的图像类型、目标设备、质量要求和预算分别是什么。
3. **一定要实测。** 质量是主观的，指标是近似的，编解码器是黑箱的——唯一可靠的结论来自拿你自己的图跑一遍。
