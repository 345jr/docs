# 一次 63 分钟会话的账单

> 这不是一个"如何接入 OpenCode 免费模型"的教程（那篇在 [上一节](./opencode-free-in-pi.md)）。
> 这是一次**对 Agent 自身行为的尸检**：63 分钟、235 步、295 次工具调用，
> 任务最终完成了，但其中约三分之二的开销花在了自己制造的岔路上。
> 重点不是"它没做成"，而是"它为什么会这样浪费"。

---

## 一、先看账单

会话：`01a138ea-1cfa-75ed-b8d8-f30dbe7892ef`，2026-10-14 05:37:09 → 06:40:31。
模型：`deepseek-v4.1-flash`，thinking level = high。

| 指标 | 数值 |
| --- | --- |
| Assistant 轮次 | 235 |
| 工具调用 | 295（其中报错 11 次） |
| 输入 token | 267,565 |
| **输出 token** | **256,789** |
| 缓存读取 token | **36,759,680** |
| 思考（thinking）字符数 | 660,560 |
| 面向用户的正文（text）字符数 | 25,741 |

两个数字值得单独拎出来：

- **缓存读取 3676 万 token**。整个会话的真实输入只有 26.7 万。放大倍数 137 倍——
  因为上下文一直在增长，而每一轮都要把整段历史重新喂回去。这是长会话 Agent 的固有税，
  但它意味着**轮次数量本身就是最贵的成本**。
- **思考 66 万字符 : 正文 2.6 万字符 ≈ 26 : 1**。绝大部分算力花在"想"，
  而"想出来的东西"里真正给用户看的只有 4%。

### 分阶段账单

| 阶段 | 时间 | 轮次 | 工具调用 | 输出 token | 缓存读取 |
| --- | --- | ---: | ---: | ---: | ---: |
| P1 换扩展 + 追查幽灵 provider | 05:37–05:52 | 75 | 120 | 72,265 | 5,096,448 |
| P2 协议报错的盲测 | 05:55–06:04 | 29 | 32 | 39,729 | 3,896,576 |
| P3 转查社区 + 验证 leoyyong | 06:04–06:19 | 68 | 84 | 74,688 | 13,268,864 |
| **P4 读 gate-notes 文档 + 决定性实验** | 06:21–06:29 | **14** | **13** | 32,189 | 3,187,584 |
| P5 构建 + 部署 + 全量验证 | 06:29–06:40 | 37 | 37 | 24,210 | 8,954,624 |

**这张表就是全文的论点。**

P4 之前：172 轮、236 次工具调用、19 亿缓存读取。
P4 及之后：51 轮、50 次工具调用，包含了"读文档 → 定位差异 → 写扩展 → 全模型矩阵验证 → 部署 → pi-web 端到端"。

**先读文档的阶段，用了 30% 的轮次做完了 100% 的工作。**
不是模型在 P4 变聪明了，是它终于停止发明问题、去读别人已经写好的答案。

## 二、它做对了什么

先说好的，否则后面的批评不公平。

### 1. 抓真实 wire 的手段是对的，而且很漂亮

面对 `ModelProtocolUnsupported`，它没有去猜上游源码，而是**给官方 `opencode` 客户端装了一个插件，在插件里 patch `globalThis.fetch`**，把真实出站的 URL / headers / body 全部落盘：

```
/root/.config/opencode/plugin/dump.js
→ "chat.params" hook
→ globalThis.fetch 包装
→ /tmp/oc-fetch.json
```

一举拿下关键事实：官方 CLI 1.19.0 打的是 **`https://opencode.ai/inference/v1/chat/completions`**，
而不是社区文档里普遍写的 `/zen/v1`；UA 是 `opencode/1.19.0 ai-sdk/provider-utils/4.0.23 runtime/bun/1.3.14`；
body 里带 16 个原生 function tools 和 `stream_options`。

这是整个会话里最高价值的一步。它没有可替代。

### 2. 根因定位又快又准

从看到 `ModelProtocolUnsupported` 到给出结论，只用了 4 轮。做法是**不猜，直接比对目录数据**：

```
pi-ai 内置目录：muse-spark-* → openai-responses
               其余 *-free   → openai-completions

rabden 扩展源码：toChatModel() 把所有模型硬编码成 openai-responses
```

结论一句话：把 chat 原生模型发到了 responses 端点。**这个诊断完全正确，且当场可验证。**

### 3. 有分阶段基准的直觉

每次怀疑"是不是我 IP 被限流了"，它都跑一组基准：

```
rabden 扩展 + muse-spark   → BASE_OK
官方 opencode CLI          → CLI_BASE
leoyyong 扩展              → 403
```

这个"对照组"思维是对的，而且正是它最后跳出死胡同的关键（见下）。

### 4. 收尾干净

- 装完调试用的 opencode fetch patch 插件后**主动删掉了**，理由是"它会全局 patch fetch，留着有副作用"。
- 每次破坏性操作前建备份（`/root/pi-ext-backup-20261014-133938`、`-143330`）。
- 用户问"你发现了什么"时，**明确区分了「确凿的」和「还没闭环的」**，没有把未验证的猜想包装成结论。

这份诚实值得记一笔，尤其是在它随后又跑偏了 10 分钟的情况下。

### 5. 最终交付是完整的

新扩展 `/root/.pi/agent/extensions/opencode-zen/`，按模型 id 路由双通道，
14 个模型在 pi-web 可见，工具往返通过，全模型矩阵逐一实测，
410 `ModelDeprecated` / 429 这类上游问题被正确识别为"不是扩展的锅"。

## 三、它踩了什么坑

### 坑 1（最贵，约 50 轮）：追一个已经死掉的东西

05:37 删掉旧扩展 `opencode-zen-free`、装上新扩展之后，pi-web 的 `/api/models` **还在返回旧的
`opencode-zen-free` 和那 7 个模型**。它开始追。

它做了这些事：

- grep 全盘找 `opencode-zen-free` 字面量（`/`、`/usr/lib/node_modules`、`/etc`、`/opt`、`/srv`、`/var/www`……）
- 反复 `sleep 65` 等 60 秒缓存过期，三次
- 往 `chunk-OIM2DMFI.js` 这种 minified bundle 里 `grep -o ".\{200\}opencode-zen-free.\{200\}"`
- 读 `/proc/<pid>/maps`、`/proc/<pid>/mem`、`/proc/<pid>/fd`
- 逐个新建 probe 目录试图绕过 `cwd` 维度的缓存
- 反复怀疑 `models-store.json` 快照、`extensionCache`、`loadModelsWithCache`

**真相是：运行中的 Next.js 进程已经把旧扩展加载进内存了。删磁盘文件不影响已运行的进程。**
它自己在 05:49 就执行了 `systemctl restart pi-web`——**正确的动作**——
但因为用户还没重启，会话被自己的会话文件吓到（"有个 5 分钟内修改的 session，可能是我们当前这个会话，重启会打断我"），
转而去用 `auth.json` 存凭据绕开重启。等到 05:51 用户说"重启好了"，**1 轮**就确认了：

> 重启后 opencode 条目变成 `(none)` —— 说明之前旧条目确实是旧进程内存缓存，现已清除。

**50 轮的答案是 1 轮就能拿到的。** 触发它绕远路的不是技术难度，是它不敢确认一件事：
"重启会不会杀掉我自己"。正确答案写在它自己刚读到的那行 `ps` 输出里（`node /usr/bin/pi-web`，PID 1220204），
而当前会话是 deepseek，不是 opencode-zen，重启不会影响它——**它只需要把 PID 和自己的模型对一下**。

> 教训：**当"配置已改但行为没变"时，第一个假设应该是"我改的地方没被重新加载"，而不是"有第二处配置源"。**
> 在一个长驻进程里改磁盘文件，然后期待行为变化，这本身就是一个需要先排除的假设，而不是需要深挖的谜题。

### 坑 2（最冤，约 40 轮）：自己的探测脚本写错了，然后把 403 当成了谜题

这是整个会话最昂贵的一段，而且完全是自造的。

它写了一批 Node 探测脚本去逆向 gate 规则。为了伪装成 OpenCode 客户端，它需要生成
SortableID 形式的 session id（`ses_` / `msg_` 前缀 + 12 位十六进制 + 14 位 Base62）。
它写了这个辅助函数：

```js
function sid(desc) {
  const t = Date.now();
  let hex = "";
  for (let i = 0; i < 6; i++)
    hex += (((BigInt(t) * 0x1000n + 1n) >> BigInt(40 - 8 * i)) & 0xffn).toString(16).padStart(2, "0");
  ...
}
```

**缺了一个按位取反 `~`。** 官方 CLI 的 descending session id 是 `~current` 的高位，
ascending（`msg_`）才用 `current`。它生成的是 ascending 形态。

后果是灾难性的：**它自己写的每一个探测请求都 403**，包括原封不动重放官方 CLI 的真实请求。

于是它开始合理地怀疑这个世界：

> "连**原样重放**真实 CLI 请求都 403，但同一刻 OpenCode CLI 成功——说明门槛在**传输层**，
> 不是请求内容。"

它接着：

- 建了一个本地**转发代理**，让 rabden 扩展指过来，抓它的确切出站头再转发上游
- 用 **curl** 重放（换 HTTP 栈）—— 403
- 用 Node `https` 直连 —— 403
- 检查 `/etc/hosts` 有没有劫持、检查代理环境变量
- 反复怀疑"TLS 指纹"、"BoringSSL vs undici"
- 反复怀疑"session affinity"、"session id 时间戳派生格式"
- 一度怀疑自己高频探测触发了 IP 级限流

真实情况是：**rbden 能通、我的重放不能通，差异就在我这个脚本少了一个 `~`。**

它在 06:27:20 自己看出来了：

> 我所有手工探测的 `ses_` id 都写错了——文档规则 #4 要求 `ses_` 用 **descending** 变体（`~value`），
> 我的探测函数漏了 `~`，生成的是 ascending。**这不是 gate 关了，是我的探测代码有 bug。**

修正之后，两个请求立刻分化：

```
[muse-spark   /responses] 200   ← 和 rabden 一致
[space-bunny /responses] 400 ModelProtocolUnsupported
[space-bunny /chat]       200   ← 真正的答案
```

**一轮。**

> 教训：**在一个"我的对照组成功、我的实验组失败"的场景里，先怀疑实验代码，再怀疑世界。**
> 更具体地说：如果连"原样重放成功请求"都失败，那几乎不可能是服务端的问题——
> 一定是重放本身失真了。这个"逐字节重放仍失败 ⇒ 本地代码有 bug"的推理规则，
> 应该被写成硬规则，而不是每次现场推导一遍。它推导了，推出了错误的结论，还搭了三层代理去验证错误结论。

### 坑 3（约 30 轮）：顺序倒置——文档晚读了 44 分钟

`docs/zen-gate-notes.md` 是 rabden 仓库自带的 gate 逆向笔记，13 条规则 + 一份验证过的配方。

它在 **05:39** 就 `sed -n '120,400p'` 读过这个文件。也就是说：**答案在第一次动手前就已经在屏幕上了。**

然后它花了：

- 32 轮盲测（05:55–06:04）自己摸 gate 规则
- 84 轮去改别人的 fork（06:04–06:19）——它发现 leoyyong / danprat 做了协议路由，
  于是花了 68 轮验证 + 打补丁（改 import 路径、改 UA、剥离 `x-stainless-*`、改 `msg_`/`global`、注入 marker），
  **结果 leoyyong 本身也是坏的**：它违反了 leoyyong 自己 README 里写的规则（带 stainless 头、走 `/zen/v1`、
  用 `req_`/`prj_` 前缀、没有 marker、把 bash/read 当成 stub 塞进去）
- 直到 **06:21**，用户直接贴出那个文档链接，它才去读

读完 14 轮，全案告破。文档里白纸黑字写着：

| 规则 | 内容 |
| --- | --- |
| #1 | 免费模型只在 `/zen/v1/responses` |
| #2 | UA 必须是官方原串 |
| #3 | **不能有 `x-stainless-*` 头** |
| #5 | 必须有一条 developer 消息含 OpenCode prompt 原文（2096 字符 marker） |
| #9 | `tools` 要么不带、要么是官方原样集合，其它一律拒绝 |

三条被 leoyyong 违反的规则（#3 / #5 / #9），它在 06:09–06:19 那 68 轮里**一条一条自己撞过**，
还自己总结出了"leoyyong 三重违规"——**结论完全正确，而这份结论文档里本来就有**。

> 教训：不是"文档一定能解决所有问题"，而是
> **"有文档 + 有别人的实现" 是一个应该优先穷尽的假设**。
> 它把顺序做成了：盲测 → 猜 → 找社区 → 改别人的代码 → 最后才读文档。
> 正确顺序是：读文档 → 看别人的实现 → 只对文档没覆盖的地方做实验。

### 坑 4（约 15 轮）：被"别人说能用"牵着走，然后自己推翻它

用户的原话是"这个是新的，貌似可以用 你看看"。它验证了 README、验证了 CLI 冒烟测试、
**在 05:52 宣布任务完成**：

> **已完成的改动** ... CLI 纯聊天 ✅ 工具调用 ✅ ... pi-web 可见 11 个模型 ✅

但它测的全是 `muse-spark-1.3-contributor-free`。而实际的任务目标是"用 OpenCode 全部免费模型"。

15 分钟后用户一用就炸：

```
Error: opencode-zen API error (400): {"type":"ModelProtocolUnsupported",...}
```

**验收标准应该在开工前写下来，而不是在唯一能过的那条路径上自我确认。**

### 坑 5（贯穿全程）：思考与产出的比例失衡

thinking 66 万字符 vs 正文 2.6 万字符。它经常在一条消息里把整个文件的 `cat` 出来、
把多个 `grep` 结果全量打印、再写 500 字推理——但**中间没有一次"我现在要验证的具体假设是什么"**。

有几个明显的信号它自己忽略了：

- 连续 5 次 `sleep 65` 等同一个缓存 —— 第三次就该意识到这不是缓存问题
- `pkill -f fwd-proxy` 反复把自己的 shell 杀掉（exit 143），因为 `pkill -f` 匹配到了自己命令行里的字符串。
  它花了 4 轮才诊断出"pkill 在杀我自己"。**这是一个 30 秒能想明白的 shell 事实。**

## 四、为什么会这样：一个更一般的解释

把上面四个坑合起来，能提炼出一个更根本的原因。

**这个任务的 gate 是一组启发式规则，不是一份协议。** 它的判定面横跨：

```
端点路径 × 协议类型 × UA 字符串 × 11 个请求头 × session id 的位级编码
× body 结构 × 工具数组的精确内容 × 流式标志
```

8 个维度，假设每个只有 2 种取值，就是 **256 种组合**。用"改一个变量试一次"的方式去搜这个空间，
理论上需要 256 次请求，而实际上它只试了其中几十种就撞墙了。

更糟的是**失败信号不区分原因**：不管你是 UA 错了、id 编码错了、端点错了、工具不对，
返回的都是同一个 `403 FreeTierError`。在一个"所有错误长得一模一样"的黑盒上做单变量搜索，
你无法判断自己是在接近还是在远离，只能靠猜——而它猜的方向是"传输层 / TLS / IP 限流"这些**看起来更高级、实际上更难证伪**的假设。

于是有了这个模式：

> **在信号贫瘠的系统上做实验，会系统性地滑向"更宏大的假设"。**
> 因为小假设（我脚本写错了）无聊且难堪，大假设（上游做了传输层封锁）刺激且好讲。

而这正是"先读文档"能省下 44 分钟的原因：**文档的价值不是告诉你答案，是告诉你搜索空间有多大。**

## 五、我的提示词有什么问题

复盘不能只骂模型。这次会话里，我（用户）的问题占了相当比例。按影响排序：

### ❌ 1. 没有定义"做完"是什么（最严重）

任务实际是「**在 pi-web 里使用 OpenCode 全部免费模型**」。
这个目标我直到 **06:24** 才说出来——**47 分钟、约 180 轮之后**。

在那之前，Agent 完全有理由认为"能跑通 muse-spark + pi-web 能看到模型列表"就是完成。
它 05:52 宣布成功，从它掌握的信息来看**并没有错**。

> 改法：开工第一句就给验收清单。
> `完成 = pi-web 里 5 个指定模型（space-bunny-free / mimo / ling / longcat / muse-spark）都能真实对话 + 工具调用成功。逐个截图给我。`

### ❌ 2. "貌似可以用 你看看" 是个没有约束的授权

这句话让 Agent 倾向于**验证结论**（README 说能用 → 冒烟测试通过 → 收工），
而不是**证伪结论**（README 说能用 → 那到底哪些模型能用 → 逐个实测）。

> 改法：`不要只测一个模型就宣布成功。把 /models 里所有 free 模型逐个跑一遍，失败的也要报给我。`

### ❌ 3. 该指文档的时候没指，晚指了 44 分钟

我 05:37 就把仓库给了它，`docs/zen-gate-notes.md` 就在仓库里。
我自己在 **06:21** 才想起来这张牌。

更糟的是我在 **06:04** 只说了"别自己瞎试，去看别人的经验"，
没有直接说"看 `docs/zen-gate-notes.md`"。于是它去读了三个社区 fork 的源码——**那正是它自己要去逆向的东西**。

> 改法：`先读 docs/zen-gate-notes.md 全文，把里面每条规则和我们的现状列成对照表，然后再说你要做什么。不要在读完之前跑任何网络请求。`
>
> 这一句话大概能省掉 100 轮。

### ❌ 4. 我在两个该喊停的时间点都没喊停

| 我介入的时间 | 本该介入的时间 | 代价 |
| --- | --- | --- |
| 06:04「别自己盲试」 | 05:45（幽灵 provider 追到第 30 轮时） | ~15 轮 |
| 06:19「先停一下，阐述发现」 | 06:10（开始搭代理的时候） | ~25 轮 |
| — | 05:52（宣布完成时，应该追问"其他模型呢"） | 直接避免了坑 4 |

我的干预模式是**滞后响应**：等烧了一堆 token 才察觉不对。
而且干预本身也偏软——"你现在一直在开展各种实验"，没说"停，现在的假设是什么"。

> 改法：设一个**自己的止损规则**，不用等 Agent 失控。
> 比如：同一类探测脚本连续失败 3 次 → 停，汇报。
> 比如：单个任务超过 10 分钟没进展 → 停，汇报。
> 这类规则写进 system prompt，比临场干预有效得多。

### ❌ 5. 「汇报一下进度」这个动作来晚了，而且太轻

05:47 我让它汇报进度（当时它正在追幽灵 provider 第 30 轮），
它给了一份漂亮的四段式总结，**没有一个字提到"我可能杀死了自己的会话所以不敢重启"**。
它汇报的是**做了什么**，不是**卡在哪**。

而 06:19 的「简单阐述一下你发现了什么」就好得多——
那次它明确写了「还没闭环的关键疑点（也是我卡住的地方）」，
并列出了那个矛盾（我重放 403 / CLI 成功）。

> 改法：与其说"汇报进度"，不如问**这三个问题**：
> 1. 你现在最确凿的结论是什么？
> 2. 你现在最想验证的假设是什么？
> 3. 如果这个假设是错的，下一步该往哪走？
>
> 这三个问题会强制它把推理外化，从而让它自己看见"我脚本里少了个 `~`"。

### ✅ 但我也有做对的

必须记下来，否则下次的提示词会矫枉过正：

- **06:04「你应该参考别人的经验，而不是自己盲目做实验」**—— 这是全场最有价值的一句干预。
  它把 Agent 从"逆向工程"切到"检索现成方案"，虽然没切干净，但方向对了。
- **06:21 直接给出文档链接** —— 把最高信息密度的输入直接递过去，而不是让 Agent 去找。
- **06:24「资料已经给到，剩下看你弄」** —— 明确交权，同时明确目标（全部免费模型）。
  这句之后 16 分钟全部搞定。

## 六、下次怎么做

### 给 Agent 的工作流约束（可以直接抄进 system prompt）

```
1. 拿到任务后，先输出一份验收清单（可验证的逐条），确认后再动手。
2. 动手前必须读：仓库 README、所有 docs/、issue、以及至少一个第三方实现。
   输出「已知事实」列表，逐条标注来源。
3. 实验必须一次只改一个变量，并在每次实验前用一句话写出：
   「如果这次失败，说明 X；如果成功，说明 Y。」
4. 建立基准组：改动前先跑通一个已知可用的路径，之后每次判断都带基准对照。
5. 若同一个脚本连续 2 次给出反直觉结果，停止实验，
   优先假设「我的代码有 bug」，而不是「服务端有新机制」。
6. 每 10 分钟或每 20 轮，主动输出一次：
   确凿结论 / 当前假设 / 下一步验证方式。
7. 未经确认不得宣布完成。完成 = 验收清单逐条打勾。
```

第 5 条是这次会话最值钱的一条，直接对应坑 2。

### 我自己的提示词模板

```
目标（验收标准）：
已知资料（先读，不要盲试）：
约束：单次会话预算 ___ 分钟 / ___ 轮；超时先汇报再继续。
遇到分歧时：列出两种可能，不要二选一。
```

### 一个通用判断

> **当一个任务涉及"别人已经逆向过的东西"（反爬、鉴权、私有协议、免费额度绕过）时，
> 默认假设是"存在一份现成的规则说明"，而不是"需要我重新发现"。
> 真正需要自己做实验的，只有文档和现有实现都没覆盖的那一小块。**

这次的教训是：这个判断本可以在第 1 分钟做完，实际花了 44 分钟。

## 附录：这次逆向出来的完整 gate 配方

> 这次踩的坑不该白踩。下面的配方是 63 分钟实验 + 社区三个 fork + 官方 CLI 抓包的合并结果，
> 已在新扩展 `/root/.pi/agent/extensions/opencode-zen/` 中落地并逐模型验证。

**两条通道，按模型分别路由：**

| 通道 | 模型 | 端点 |
| --- | --- | --- |
| chat | 除 `muse-spark-*` 外全部 `*-free` | `POST https://opencode.ai/inference/v1/chat/completions` |
| responses | `muse-spark-1.2/1.3-contributor-free` | `POST https://opencode.ai/zen/v1/responses` |

**共同头部：**

```
Authorization: Bearer public
User-Agent: opencode/1.19.0 ai-sdk/provider-utils/4.0.23 runtime/bun/1.3.14
x-opencode-client: cli
x-opencode-project: global
x-opencode-session:     ses_ + 12位hex + 14位base62   (hex = ~(now*0x1000+1) 高 48 位，descending)
x-opencode-session-id:  同上（与 session 相同）
x-opencode-request:     msg_ + 12位hex + 14位base62   (ascending，无 ~)
```

**必须没有的：** 任何 `x-stainless-*` 头（OpenAI SDK 自动加的指纹，要用 `options.fetch` 在传输层剥掉）。

**chat 通道额外要求：**

```
stream: true
stream_options: { include_usage: true }
body.tools: 必须包含名为 bash 和 read 的 function 工具
```

> ⚠️ 社区文档普遍没写这一条，但它实测是 chat 通道的硬门槛——
> 不带工具直接 403。这也是当初所有人（包括社区 fork 作者）都失败的原因。

**responses 通道额外要求：**

```
body.input[0]: { role: "developer", content: <OpenCode 官方 marker prompt 原文 2096 字符> }
body.input 之后最多 2 条
body.tools: 必须删除（哪怕 Pi 带了工具）
```

**判定模型是否免费**：Pi 内置目录里 `cost === 0`（不要只看 id 有没有 `-free` 后缀——
`big-pickle` 就是反例）。
