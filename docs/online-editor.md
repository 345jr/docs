# 在线编辑模块设计

本文记录这个文档站「在线编辑」功能从 0 到 1 的完整过程：为什么要做、为什么选 Tiptap、前后端怎么分工、中间踩了哪些坑、最后怎么验证上线。整个模块分两部分——**Docusaurus 前端（`/editor` 页面）** 和 **Steward 后端（`/docs-api/docs-editor/`）**。

## 一、目标：三个核心点

需求很明确，只有三件事：

1. **密钥进入编辑专区**——编辑页是公开 URL，不能让 token 写死在 JS 里，必须有解锁门槛。
2. **能编辑文章排序、能放进分类**——也就是改 `sidebar_position` 和移动文件到分类目录（含多级分类），这是旧版没有的能力。
3. **富文本要正常**——这是上次失败的地方，核心功能被编辑器本身搞坏了。

:::tip[一句话结论]
架构上最省事的做法：**编辑器只负责「写文件 + git commit + push」**，构建部署完全复用现有的 GitHub Actions + Steward 流程，服务器上不跑构建。
:::

## 二、技术选型：为什么是 Tiptap

上一版用的是 Milkdown。它的 WYSIWYG 体验其实不差，但和「Docusaurus Markdown 站点」这个场景错位——尤其是 admonition（ `:::tip[标题]`）的 round-trip 极不稳定，最后核心的富文本编辑反而不可用，所以才整体推倒重来。

这次换 **Tiptap v3**，关键结论（用 Context7 查官方文档得到）：

- Tiptap 有**官方 `@tiptap/markdown`**（基于 marked），支持 `contentType: 'markdown'` 载入、`editor.getMarkdown()` 导出，天然适配 Markdown 站点。
- 提供 `markdownTokenizer` / `parseMarkdown` / `renderMarkdown` 扩展点，可以**精确 round-trip 任意语法**，这正是 Docusaurus admonition 需要的。
- React 19 官方支持；SSR 场景下用 `immediatelyRender: false` 即可。


| 维度          | Milkdown                 | Tiptap（本次）                    |
| ----------- | ------------------------ | ----------------------------- |
| Markdown 往返 | 需要自己写较多转换，易坏             | 官方 Markdown 扩展，稳定             |
| 自定义语法       | 自定义 ProseMirror 节点，调试成本高 | tokenizer + parse/render，接口清晰 |
| 生态 / 维护     | 活跃                       | 活跃，扩展丰富                       |
| 心智负担        | 对「富文本 → Markdown」不友好     | 原生面向 Markdown                 |


## 三、整体架构

```
浏览器 /editor 页
   │  解锁密钥 → session token（存 sessionStorage）
   │  tree / read / save / move / delete / category / status
   ▼
nginx  location ^~ /editor/api/  →  proxy_pass  http://127.0.0.1:9092/docs-api/docs-editor/
   ▼
Steward  internal/docseditor + internal/handlers/docseditor.go
   │  写文件 + git commit + git push（复用 gitstatus collector）
   ▼
GitHub 仓库 pushes → Actions 构建 → docs-latest release
   ▼
Actions 回调 Steward /deploy/webhook  →  解压部署到 /var/www/docs
```

分工很清楚：**前端只做编辑体验，后端只做「落盘 + 推送」，构建部署走原链路。**

## 四、后端（Steward）

代码集中在三个地方：

- `internal/docseditor/editor.go`——文件系统 + git 操作。
- `internal/docseditor/session.go`——解锁密钥换短期 session。
- `internal/handlers/docseditor.go`——HTTP 接口层。

### 接口清单

所有接口挂在 `/docs-api/docs-editor/` 下，除 `unlock` 外都要求 session。


| 接口                 | 方法   | 作用                            |
| ------------------ | ---- | ----------------------------- |
| `/unlock`          | POST | 密钥换 24h session token         |
| `/status`          | GET  | 查 docs 的 GitHub Actions 流水线状态 |
| `/tree`            | GET  | 返回分类 + 文章目录树（含元信息）            |
| `/read`            | GET  | 读取单个文件                        |
| `/save`            | POST | 新建/更新文章，可携带分类                 |
| `/move`            | POST | 移动/改名，可同时覆写内容与创建分类            |
| `/delete`          | POST | 删除文章                          |
| `/category`        | POST | 新建/更新 `_category_.json`       |
| `/category/delete` | POST | 删除空分类                         |
| `/reorder`         | POST | 批量重排/移动分类与文章（一次提交）            |


### 鉴权与密钥

密钥存在 Steward 的 `.env`（`STEWARD_DOCS_EDITOR_KEY`），浏览器解锁后拿到随机 session token，后续请求用 `Authorization: Bearer` 带上。

- 密钥只在 `unlock` 时使用一次；
- session 24h 过期，存 `sessionStorage`，关浏览器即失效；
- `/docs-api/` 这个挂载点**不做 open token 校验**，避免把 Steward 的 open token 暴露到浏览器。

### 写文件 = commit + push

`Editor` 复用了已有的 `gitstatus.Collector`：它自带 GitHub token 注入、路径校验、并发串行化。每次写操作都用一把 `writeMu` 串行化「改工作区 + commit + push」，避免并发编辑互相覆盖。

推送失败时**保留本地 commit**（返回 `pushed: false`），不阻塞下一次保存。

### 分类与排序模型

Docusaurus 的侧边栏是 `autogenerated`，所以：

- **分类** = `docs/` 下的目录，元信息在 `_category_.json`（label / position / link.description）。
- **排序** = 文章 front matter 的 `sidebar_position`，以及分类的 `position`。
- **归属分类** = 文件所在的目录路径（未必需要 `_category_.json`，没有时 Docusaurus 用目录名兜底）。

目录树接口会解析 front matter（`title` / `sidebar_position`）和 `_category_.json`，按 position 排序返回，前端直接展示出「和站点一致」的顺序。

### 排序管理（自由拖拽）

顶栏「新建分类」右侧的「排序管理」打开一个模态框，展示整棵目录树，支持自由拖拽：同级排序、把文章拖进任意分类、把分类拖进另一个分类（含挪到根目录）。因为是全量重排，落到后端是一个聚合接口：

- 前端提交整棵树（每个节点带**原路径**，层级决定新父分类）；
- 后端按展开顺序重新分配分类的 `position` 与文档的 `sidebar_position`，把节点物理移动到新目录；
- 只允许「重排 + 移动」，节点集合必须与当前完全一致，**不允许增删**（防止误删）；
- 所有改动合并成**一次 commit + push**。如果逐个调用 `/save`、`/category`，会产生 N 个 commit、N 次构建，而 docs 的 workflow 是 `cancel-in-progress`，必然互相取消，所以必须批量。

保存后模态框不立即关闭，顶部按「排队 → 构建 → 完成」三步骤展示本次 commit 对应的流水线，成功后才允许关闭。

### 路径与扩展名校验

安全底线：

- 禁止 `..` / `.` / 空段 / 绝对路径 / `~` / `\`，防止路径逃逸；
- 文章只允许 `.md` / `.mdx`；
- 分类删除只允许空目录，避免误删内容。

### 流水线状态查询

`GET /docs-editor/status` 复用 `githubstatus.Client`，查询 docs 仓库最近几次 workflow run，返回 `busy`（有 `queued` / `in_progress` 的 run）。这是前端保存前置检查的依据。

## 五、前端（Docusaurus）

页面在 `src/pages/editor.tsx`，Tiptap 相关自定义在 `src/theme/tiptap/`。

### 页面结构

进入后是三段布局：顶部**子顶部栏**（文件路径与模式徽标、元信息/源码/删除/保存等动作、新建文章/新建分类/排序管理、流水线指示点、退出），左侧是**可收起侧栏**（待创建分类 + 文件树，底部收起按钮对齐文档站），中间是**文章编辑区**，右侧栏只有**锚点目录**（按 H1–H3 生成，点击跳转、滚动高亮，观感对齐文档页 TOC）；文章元信息通过顶部栏「元信息」按钮在**模态框**中编辑。

### Tiptap 集成

编辑器用 `@tiptap/react` + `StarterKit` + `Markdown` + `TableKit` + `Image` + 自定义 `Admonition`：

```ts
useEditor({
  extensions: [
    StarterKit.configure({heading: {levels: [1, 2, 3, 4]}}),
    Markdown.configure({markedOptions: {gfm: true, breaks: false}}),
    TableKit,
    Image,
    Admonition,
  ],
  content: initialMarkdown,
  contentType: 'markdown',
  immediatelyRender: false, // SSR 安全
  onUpdate: ({editor}) => onChange(editor.getMarkdown()),
})
```

工具栏覆盖标题、加粗/斜体/删除线、行内代码、列表、引用、代码块、分割线、链接、图片、表格、提示框。`.mdx`（含 JSX）自动切源码模式，任何文章也能手动切源码兜底。

### admonition 自定义节点

这是整个模块最关键的一段。Docusaurus 语法是  `:::tip[标题]`，Tiptap 通过一个自定义 block 节点精确往返：

```ts
markdownTokenizer: {
  name: 'admonition',
  level: 'block',
  start: (src) => src.indexOf(':::'),
  tokenize: (src, _tokens, lexer) => {
    const match = /^:::(\w+)(?:\[([^\]]*)\])?\r?\n([\s\S]*?)\r?\n:::(?:\r?\n|$)/.exec(src)
    if (!match) return undefined
    const [, type, title, text] = match
    return {type: 'admonition', raw: match[0], admonitionType: type,
            admonitionTitle: title ?? null, tokens: lexer.blockTokens(text)}
  },
},
```

节点本身用 `ReactNodeViewRenderer` 渲染成带类型下拉 + 标题输入的提示框，内层内容可编辑。

### Markdown 往返验证

因为上次就是栽在 round-trip 上，这次专门写了一个 Node 脚本，把现有全部 `.md` 用 `MarkdownManager` 解析再序列化，检查：

1. **语义等价**（忽略空白、表格对齐、转义差异后逐行对比）；
2. **幂等**（第二次序列化 == 第一次）。

结果全部通过。过程中修掉的两个问题（见「踩坑记录」）。

### 新建文章 = 草稿，不提前提交

点「新建文章」只在前端生成一个**草稿**（path / front matter / 正文），**不调用任何写接口**；只有点「创建并发布」才产生一个 commit。这就是之前「创建即提交、且提交空内容」问题的修复。

### 分类暂存与合并提交

新建分类先在前端**暂存**；保存文章到该分类时，把分类元信息放进 `/save` 或 `/move`，后端在该目录还没有 `_category_.json` 时一并写入——**分类和文章同一个 commit**。左侧「待创建分类」也提供「立即创建」用于单独建分类。新建文章/新建分类都不再填排序字段，默认追加到所属层级的**最后**（没有 position 的条目排在已排序条目之后）；需要调整位置时用「排序管理」。

### 流水线前置检查与等待

- 每次写操作前先查 `/status`，`busy` 就 toast 阻止。
- 提交成功后按返回的 commit 轮询对应 workflow，toast 依次反馈「等待 CI 启动 → 构建部署中 → 完成 / 失败」。

:::warning[为什么必须先检查]
docs 的 workflow 配了 `concurrency: cancel-in-progress: true`。如果在上一个构建还在跑时再 push，**正在跑的构建会被取消**。所以「运行中就阻止」不是锦上添花，而是防事故。
:::

## 六、部署链路

1. Steward 后端推送 → `backend.yml` 构建 `steward-backend.zip` → 回调 `/deploy/webhook` 自更新。
2. 前端/文档推送 → `deploy.yml` 构建 → 发布 `docs-latest` release → 回调 Steward，解压到 `/var/www/docs`。
3. nginx 的 `docs.lopop.top` vhost 增加：

```nginx
location ^~ /editor/api/ {
    proxy_pass http://127.0.0.1:9092/docs-api/docs-editor/;
    include snippets/proxy-common.conf;
}
```

同源请求，没有 CORS 问题。

## 七、测试

- **后端单测**：`internal/docseditor` 用临时 git 仓库覆盖增删查改、分类随文章一次提交、路径逃逸、扩展名校验；`internal/handlers` 用 `httptest` 覆盖解锁、session、各接口与错误分支。
- **Markdown 往返**：上述 Node 脚本。
- **浏览器 E2E（Playwright）**：本地构建 + 线上站点各跑一轮。验证解锁、文件树、富文本挂载、admonition/表格渲染、源码模式输出、编辑生效；并用 mock 拦截写接口，验证「草稿阶段 0 写请求」「保存 payload 正确携带分类」「busy 时保存被拦截」。

## 八、踩坑记录

1. **admonition 关闭符必须独占一行**
 最初 `renderMarkdown` 输出成 `内容:::`,再次解析时 tokenizer 匹配不上，方括号被转义成 `\[标题\]`，越改越乱。修成 `内容\n:::` 后幂等。
2. **末尾空行会滚雪球**
 提示框作为最后一个块时，序列化会在文件尾不断追加空行。前端保存前 `body.replace(/\s+$/, '')` 兜底。
3. **表格序列化差异是正常的**
 Tiptap 会把表格列对齐、并把 `_` / `~` 转义（`node_modules` → `node\_modules`）。语义等价且稳定，不需要强行还原。
4. **SSR**
 Docusaurus 构建时会 SSG，Tiptap 必须 `immediatelyRender: false`，页面再用 `mounted` 状态兜一层。
5. **CI 回调偶发 502**
 如果后端在自更新重启时正好收到 docs 的部署回调，会 502。解决：先推后端、等自更新完成，再推前端；必要时用 `/control/ops/docs/restart` 手动重拉 release。
6. **别让「新建」偷偷提交**
 创建文章/分类都先暂存，等用户编辑完再一次性提交，否则会产生多余的 commit 和构建。
