# SkyDrop 缩略图优化：把图像压缩的知识用起来

前阵子读了 MDN 的图像格式三部曲（读后总结见[图像为什么可以被压缩](../web-articles/image-formats-three-parts.md)），三篇原文分别是：

1. [Color models for humans and devices](https://developer.mozilla.org/en-US/blog/color-models-humans-devices/) —— 人眼与设备如何感知颜色
2. [Pixel data from encoders to decoders](https://developer.mozilla.org/en-US/blog/image-formats-pixels-graphics/) —— 编解码器流水线
3. [Codecs and compression tools](https://developer.mozilla.org/en-US/blog/image-formats-codecs-compression-tools/) —— 格式与工具的实战选型

读完之后一个很自然的动作是：**拿着文章里的结论，去对照自己项目的现状**。SkyDrop 是我自托管的文件分享服务（Go 后端 + React 前端），图片/视频列表重度依赖缩略图。对照下来发现了好几处值得改的地方，最终落地为四次提交。这篇记录整个过程。

## 对照出来的问题

| 文章里的观点 | SkyDrop 的现状 |
|---|---|
| 第一篇「From camera to screen」：设备色彩/方向元数据需要被尊重 | Go 的 `image.Decode` 忽略 EXIF orientation，手机竖拍照片缩略图会横躺 |
| 第三篇开头的问题清单：「你要展示大图还是缩略图？」 | 网格卡片（显示约 300px 宽）和全屏预览共用同一张 1280px 缩略图 |
| 第二篇的 note：给 `<img>` 设宽高，避免 layout shift | 占位写死 4:3，竖图加载完会跳动 |
| 第三篇第一条建议：优先用按需处理的云服务 | R2（Cloudflare 对象存储）文件的卡片**直接加载公网原图**，几 MB 一张 |
| （文章没提，但属于同一体系的空白） | 视频没有缩略图，卡片只是占位图标 |

也有已经做对的：统一输出 JPEG 而非 PNG（第三篇：尽量别用 PNG）、Go stdlib 编码器默认 4:2:0 色度下采样（第二篇的核心手段）、`loading="lazy"`（第三篇：不可见不加载）、异步预生成而非实时压缩。这些不用动。

## 四轮迭代

### 1. EXIF 方向校正

手机竖拍照片（orientation=6）生成的缩略图会横躺——这是最影响观感的实际问题。为了保持项目**纯 Go 无 cgo**的约束（当初选 `modernc.org/sqlite` 也是这个理由），手写了一个 JPEG APP1/EXIF 解析器（约 100 行），生成缩略图前先按 orientation 转正再缩放，同时把「显示宽高」（90°/270° 时交换宽高）一并算出来。

### 2. 尺寸分档 + 真实宽高比占位

一次解码产出两档：**1280px/Q82**（全屏预览）+ **480px/Q80**（网格卡片）。`files` 表加 `width`/`height` 列，上传时只读文件头记录显示尺寸，前端网格按真实宽高比占位。升级时靠已有的 `spec.json` 机制自动全量重建一次。

实测效果：一张 2400×1800 的照片，网格小图 **3.5KB**，原来的单档 20KB——**网格带宽省约 83%**，一屏几十张卡片差距非常明显。

### 3. R2 回源缩略图

第三篇建议优先用 Cloudflare Images 这类按需处理服务，但我用的是 free tier，没有 Image Resizing。于是做了自托管的等价物：浏览器直传 R2 后，`confirm` 接口异步把对象**回源下载到中心**，复用现有流水线生成双档缩略图、顺手记录宽高。之后列表卡片走本地缩略图，下载原图行为不变（仍回源 R2）。

实测 R2 图片网格卡片从 ~68KB 原图降到 **3.5KB（5%）**。R2 出口流量免费，代价只是中心一次性回源。首次部署会自动 backfill 所有存量 R2 图片。

### 4. 视频封帧

文章没讲这个，但属于缩略图体系的自然延伸。项目本来就依赖 ffmpeg（MOV 转码），于是：本地视频抽 1s 处帧（失败回退第 0 帧，避开纯黑片头）走同一套双档流水线；**R2 视频不用整段下载**——ffmpeg 直接读 URL（HTTP range 请求），未配公开域名时用预签名 GET。ffmpeg 解码还自动应用旋转元数据，竖拍视频也是正的。

一个细节：视频的 `preview=1` 默认**仍然流原视频**（全屏播放需要），只有网格小图（`size=small`）和显式缩略图下载才给封帧，避免 `<video>` 标签收到一张 JPEG。

## 没做什么，以及为什么

文章的价值不仅在于「该做什么」，也在于帮人判断「不用做什么」：

- **没有换 WebP/AVIF 编码**。第三篇的关键结论是「同一格式内部的差异，常常比格式之间还大」，而项目坚持纯 Go——换 MozJPEG/libwebp/AVIF 都要引入 cgo 或外部进程，性价比低。收益在尺寸分档，不在换格式。
- **没有做渐进式 JPEG**。第二篇说交错「几乎免费」，但 Go stdlib 只出 baseline，缩略图本身不大，收益有限。
- **没有改 gamma 线性缩放**。理论上应在线性光下缩放，直接在 sRGB 值上插值会让暗部略偏暗——但主流 Go 图像库都这么做，观感差异可接受。
- **全屏预览保持原图**。这是项目自己的设计决策（点开就看原图），不盲目套用「全部缩略图化」。

## 方法论上的两点收获

**「参数不对等，比较就没有意义」**——第三篇里 AVIF 被设成 12-bit/YUV444 导致「输给」JPEG 的例子印象深刻。这次没有拍脑袋换格式、调参数，就是受这个提醒：先把尺寸分档这种「确定性收益」做掉，参数微调留到有真实数据再说。

**「一定要实测」**——每一轮改动都做了两层验证：单元级（构造红蓝半图 + 注入 EXIF 标签，像素级验证旋转方向正确）和端到端（起冒烟实例走完整上传链路，R2 改动直接用真实 bucket 跑了一遍 presign→PUT→confirm→删除的全流程，确认零残留）。

三篇文章表面上在讲「选哪个格式」，实际上回答的是「为什么图像可以被压缩」。而把这条链路真正走一遍之后才发现：**格式之争从来不是重点，理解你的场景（卡片还是预览、本地还是对象存储、原图还是封帧），然后让每个场景只加载它需要的信息量**——这才是压缩知识在工程里的正确用法。
