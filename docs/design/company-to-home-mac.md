# 从公司连回家的 Mac

人坐在公司的 Windows 前，要看到家里 Mac 的桌面，并且鼠标键盘都跟手。免费、开源，不使用 ToDesk 这一类商业远控。

2026-11-16 在公司那台电脑上实际连过，画面是通的。

## 先把方向说清楚

一开始容易想反：家里的 Mac 去连公司的 Windows。那条路公司自己的远程桌面就能走，macOS 也装了 Windows App。但要的是反过来——**公司是操作的那一端，家里的 Mac 是被看的那一端**。

Mac 不能当远程桌面（RDP）的主机。能当主机的是公司这台 Windows 11 专业版。所以协议换成 RustDesk：两端都是客户端，中间有一台自建的登记服务器。

## 为什么服务器必须放在公司

家里的 Mac 有公网 IPv6，从公司却连不进去。不是系统更新把入站关掉了。

macOS 27.2 的防火墙是关的，也没有第三方网络扩展。公司去 ping 这个 IPv6 时，Mac 自己的「收到回声请求」计数一动不动。包没进内核，在门口就被丢了。网关是一台中国电信的智能网关，行为是：**没有从里面先发出去的连接，外面进来的单播一律丢掉**。家里另一台 Windows 的局域网地址，以前就被同一台光猫这样丢过。

所以任何「公司主动连回家」的做法都不会通，包括把 Mac 的屏幕共享端口暴露出去。能通的只有 Mac 先往外拨，公司再顺着这条已经打开的洞回来。

服务器放哪，决定画面卡不卡。同一时刻量过的往返时间：

| 路径 | 大约延迟 | 不用的原因 |
| --- | --- | --- |
| 家里 Mac → 公司 IPv6 | 6 毫秒，后来登记往返测到 3 毫秒 | 就用这条 |
| 家里 → 美西 VPS | 130–150 毫秒，还有丢包 | 绕地球一圈 |
| 公共 RustDesk 中继（纽约） | 230 毫秒，中继端口直接拒绝 | 又远又不可控 |

VNC 再套一层 SSH 也能借这 6 毫秒，但 VNC 的画面本身糊。RustDesk 的登记和中继都放在公司电脑上，Mac 只主动向外连接，画面仍走这 6 毫秒，不借别人的服务器。

## 实际装了什么

两边都是 RustDesk 1.5.3，公司上的服务端是 rustdesk-server 1.1.16。服务端两个进程：

- `hbbs`：登记。别人问「这台 Mac 现在在哪」，它回答。监听 21116（TCP 和 UDP）、21115（给打洞做的额外端口）、21118（网页套接字）。
- `hbbr`：中继。两端打洞失败时，画面从这里过。监听 21117，另外留了 21119。

它们用计划任务挂在 SYSTEM 下，开机就起。防火墙只加了这几个端口，原来的 22、3389、ICMPv6 没动。密钥是服务端第一次启动时自己生成的，两个客户端的配置里写的是同一把公钥。中继地址不在服务端写死：每一端把自己配置的登记主机当作中继，这样地址变了只改客户端。

家里 Mac 上装了客户端，但不靠人打开窗口。一个登录项负责 `RustDesk --server`，人登录着、机器不睡眠时它就在。另一个登录项每 5 分钟问一次公司电脑现在的 IPv6，写进配置，变了就重启这个服务。公司侧的宽带前缀会漂，后缀 `::236` 是稳定的那一个，脚本优先认它。

公司上的客户端指向同一个地址和同一把公钥。Mac 的 ID 是 `427872087`。永久密码只留在两台机器的配置里，不写在这篇里。连接方式设成「只用永久密码」，这样人在公司时，不用先跑回家里点接受。

## 两个不看日志就会以为没装好的问题

### 登记地址写了，回包却从另一个地址出去

公司这块网卡上同时有三个全局 IPv6，而且都允许被拿来当源地址：

- `…::236`，DHCP 下来的 `/128`，这是我们想用的
- 一个无状态自动配置的 `/64` 地址
- 一个已经弃用的临时地址

Mac 把登记包发给 `::236`。Windows 回包时挑了那个自动配置地址。家那边的防火墙只认「从我刚刚写过的那一台回来」的包，源地址一对不上，回包就被丢。表现是 Mac 一直在重试登记，服务端其实已经收到了。

处理是把另外两个地址标成「不要拿来当源地址」，只留 `::236`。公司上另有一个每 5 分钟跑的计划任务，防止租约刷新之后这个标记丢了。改完再探，7.9 毫秒就收到了登记成功。

### 成功了，客户端却说不认识这个答复

服务端对同一台机器，6 秒内登记公钥超过两次，就不再认真处理，只回一个「太频繁」。客户端 1.5.3 只把「成功」「UUID 不一致」「还没部署」当成数完了；「太频繁」落到一条「未知的登记答复」里，于是本地永远记着「密钥未确认」，每 3 秒再登记一次。计数器只在进程内存里，不回复就不会冷却，于是永远太频繁。

协议本身没坏。把服务端重启，让 Mac 安静地登记一次，回来的是空的成功答复，`key_confirmed` 变成 true。之后不要在它重试的时候反复重启，否则又会把自己打进这个循环。

另外，开源的 `hbbs` 不听 21114。那是专业版的 HTTP 接口。日志里对 `/api/heartbeat`、`/api/sysinfo` 的超时可以忽略，不影响登记和画面。

## 怎么走到画面

公司那端向登记服务器问这台 Mac。Mac 因为一直挂着外连，登记服务器知道它当前的 IPv6 和端口。两端再互相打一个 TCP 洞。实测这一步大约 15 毫秒，洞打在 Mac 自己的公网地址上，没有绕去中继。打洞记成的 NAT 类型是「不对称」，这种类型通常会逼人走中继；这次 IPv6 下仍然直接打通了。

中继留着当退路。同一台 Mac 自己连自己的那次，对端主动要求走中继，4.9 毫秒建好。那是测试，不是日常路径。

画面和键鼠还各要一次系统权限，只能在 Mac 上点：

- 隐私与安全性 → 屏幕录制 → RustDesk
- 同一页的辅助功能 → RustDesk

没有屏幕录制就只有连接、没有画面。没有辅助功能就只能看、不能动。服务跑在登录用户下面，不另装一个要管理员密码的系统守护进程；人在公司时，家里这台保持登录、并且不要睡死。

## 到公司以后

打开公司上的 RustDesk，输入 `427872087` 和那组永久密码。服务器地址和密钥已经写在配置里，不用再填。

地址漂了不用手改。家里每 5 分钟会向记录公司地址的那个服务要一次当前 IPv6，仍然优先 `::236`。
